# Диагностика подключения к OpenRouter

Проверку выполняйте из того же окружения, где запущен backend:

```bash
backend/.venv/bin/python scripts/doctor.py
```

Скрипт проверяет DNS и доступность HTTPS-каталога моделей. Он не отправляет API-ключ и не проверяет оплату либо генерацию. Для Docker выполняйте проверку внутри контейнера backend: успешное подключение на хосте не подтверждает доступ контейнера к сети.

Если DNS возвращает адрес из `198.18.0.0/15`, скрипт сообщает о fake-IP DNS. Маршрут backend или контейнера должен проходить через соответствующий VPN; альтернативой служит доступный HTTP-прокси. Ошибка DNS не исправляется заменой ключа или модели.

Локальный backend читает `.env` из корня до импорта провайдеров. Можно задать `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY`; например, исключить из прокси `localhost,127.0.0.1,searxng,executor`. Не публикуйте URL прокси с логином и паролем. После изменения окружения перезапустите backend.

Compose передаёт контейнеру только явно перечисленные переменные. Для прокси добавьте локальный override с нужными переменными в `services.app.environment` или `services.backend.environment`. Адрес `127.0.0.1` внутри контейнера относится к самому контейнеру; прокси на хосте должен быть доступен по адресу хоста в Docker-сети. Не копируйте `.env` или ключи в образ.

Если HTTPS работает, а запрос модели отвергается, проверьте ключ в админке, доступность выбранной модели и сообщение провайдера. Настройки из БД имеют приоритет над окружением; редактирование `.env` не заменяет уже сохранённый ключ. `scripts/doctor.py` не устанавливает готовность конкретной модели или валидность ключа.
